# version-bump

Quark's version string lives in **eight** places. The project guidance (CLAUDE.md, README) only names three — the README shields.io badge, the `Cargo.lock` `quark` entry, the iOS `Info.plist`, and the xcodegen `project.yml` are easy to forget, and they have historically been bumped late in separate commits (the plist drifted to `0.11.3` while the tree was at `0.12.0`; `project.yml` silently sat at `0.5.0` until the tree reached `0.17.2`, because nothing updated *or* checked it). This skill changes all eight together and refuses to run if they're already out of sync.

| # | File | Where the version appears |
|---|------|---------------------------|
| 1 | `package.json` | `"version": "X.Y.Z"` |
| 2 | `src-tauri/Cargo.toml` | `[package]` → `version = "X.Y.Z"` (first occurrence only — **not** dependency versions) |
| 3 | `src-tauri/tauri.conf.json` | `"version": "X.Y.Z"` |
| 4 | `README.md` | shields.io badge: `version-X.Y.Z-<color>` |
| 5 | `src-tauri/Cargo.lock` | the `quark` package block (also regenerated by any `cargo build`, but synced here so the tree is clean immediately) |
| 6 | `src-tauri/gen/apple/quark_iOS/Info.plist` | `CFBundleShortVersionString` (`<string>X.Y.Z</string>`) |
| 7 | `src-tauri/gen/apple/project.yml` | `CFBundleShortVersionString`, once per iOS target (the app and `QuarkNSE`). xcodegen stamps this into the built app, so it must match the plists. Every target's copy is read — the extension's used to be assumed to follow from the global rewrite, which is how it could sit at an older version through both the drift guard and the post-rewrite verify |
| 8 | `src-tauri/gen/apple/QuarkNSE/Info.plist` | the notification service extension's `CFBundleShortVersionString`. App Store validation **rejects an extension whose version differs from its host app's**, so this is a build failure waiting to happen, not a tidiness issue |

## The iOS build number (`CFBundleVersion`)

`CFBundleVersion` is **not** the version, and the script no longer treats it as such.

App Store Connect requires the build number to **strictly increase across every upload sharing one `CFBundleShortVersionString`**. If it tracked the marketing version, each release would permit exactly one upload — and the second attempt (a rejected build, a signing fix, a re-archive) would be refused *after* the archive was already built and signed, with no way forward but a version bump that misrepresents the release.

So it is an **integer that never resets**, independent of the version, living in four places:

| File | Key |
|------|-----|
| `src-tauri/gen/apple/quark_iOS/Info.plist` | `CFBundleVersion` |
| `src-tauri/gen/apple/QuarkNSE/Info.plist` | `CFBundleVersion` |
| `src-tauri/gen/apple/project.yml` | `CFBundleVersion`, once per iOS target |

Those four must agree with each other, for the same reason the version must: validation rejects an app and extension that disagree. The script checks this on **every** run — including a plain version bump — so a hand-introduced drift surfaces at the next bump instead of at an upload.

```bash
bash .claude/skills/version-bump/bump.sh build      # 3 -> 4
bash .claude/skills/version-bump/bump.sh build 10   # set explicitly (must increase)
```

**Bump it once per upload to App Store Connect**, not per release and not per commit. A version bump leaves it alone, and asserts afterwards that it was left alone.

## When to bump (timing)

**Bump once per branch, when prepping it for merge — not eagerly while the feature is still in progress.** A single branch often lands several feature/fix commits; bumping on each one churns the eight version files, produces noisy intermediate versions, and is the main source of the cross-file drift this skill exists to prevent. So:

- ✅ The branch is otherwise ready to merge (work complete, tests green) → bump once, with the **highest** SemVer level any commit on the branch warrants (one feature commit anywhere ⇒ minor, even if the rest are fixes).
- ❌ Mid-feature, just after a single commit, or "to be safe" before more work lands on the same branch → don't bump yet.
- If you're unsure whether the branch is at merge-prep, ask the user before bumping.

This timing supersedes any "bump whenever shipping a feature or fix" phrasing — the per-commit reading caused the drift, so we bump per-merge instead. (CLAUDE.md's Versioning section is aligned with this.)

### Don't re-bump a version that hasn't shipped yet

Before bumping, check whether the **current** in-tree version has actually been released. A version ships when CI tags its release commit `vX.Y.Z` (`release.yml` runs on `v*` tags). If the current version was never tagged, it's still **unreleased** — your new changes can ride that pending version, and bumping again just mints a number that never ships.

- The version in `package.json` is `0.15.3` but there's no `v0.15.3` tag, and your branch is **another patch fix** → **don't bump.** `0.15.3` already covers patch-level work; it just hasn't gone out yet.
- Same situation, but your branch adds a **feature** while the pending `0.15.3` is only a patch ahead of the last release → **do bump**, to `minor` (`0.16.0`). You're *escalating the SemVer tier* of the unreleased version, not stacking a redundant increment.

The script enforces this: it aborts a redundant bump of an unreleased version (one whose tier doesn't exceed what the pending version already advanced past the last release) and tells you why. It relies on release tags being present locally, so `git fetch --tags` first if you're unsure. To bump anyway, re-run with `ALLOW_UNSHIPPED_BUMP=1`.

## SemVer rule (from CLAUDE.md)

- **Feature** — new user-visible behaviour → bump **minor** (`0.4.1 → 0.5.0`)
- **Bug fix** — corrects existing behaviour, no new features → bump **patch** (`0.4.1 → 0.4.2`)
- **major** is reserved for breaking/milestone releases — only when the user explicitly asks.

If you're unsure whether the change is a feature or a fix, ask the user before bumping.

## How to run

From the repo root:

```bash
bash .claude/skills/version-bump/bump.sh <major|minor|patch|X.Y.Z|build [N]>
```

Examples:

```bash
bash .claude/skills/version-bump/bump.sh minor    # shipped a feature
bash .claude/skills/version-bump/bump.sh patch     # shipped a bug fix
bash .claude/skills/version-bump/bump.sh 1.0.0      # explicit version
bash .claude/skills/version-bump/bump.sh build       # next TestFlight upload
```

The script:
1. Reads the current version from `package.json` (the source of truth).
2. **Aborts if the eight files don't already agree** — printing which one drifted (naming the `project.yml` key explicitly, since its build number is checked separately), so you reconcile an existing mismatch rather than burying it.
3. **Aborts if the four build numbers don't agree**, or if the build number isn't an integer. This runs on every invocation, `build` and version bumps alike.
4. On `build`: increments (or sets) the build number, refusing any value that doesn't strictly increase, then verifies and exits without touching the version.
5. Computes the new version (or takes the explicit one).
6. **Aborts a redundant bump of an unreleased version** — if the current version has no `vX.Y.Z` release tag and the requested bump wouldn't escalate its SemVer tier (see ["Don't re-bump a version that hasn't shipped yet"](#dont-re-bump-a-version-that-hasnt-shipped-yet)). Override with `ALLOW_UNSHIPPED_BUMP=1`.
7. Rewrites all eight with substitutions anchored on the `CFBundleShortVersionString` key (dependency versions in Cargo.toml/Cargo.lock, the iOS deployment target, and the build number are all left alone).
8. Verifies each file now reports the new version, **asserts the build number was not altered**, and prints the changed lines.

It only edits the working tree — it does **not** commit, tag, or push. Review `git diff`, then commit as usual.

## Notes & gotchas

- **Don't hand-edit just one file.** That's the exact drift this skill exists to prevent. Always go through the script.
- **Cargo.lock**: the script updates only the `quark` entry. A later `cargo build` will reproduce the same change, so either order is fine.
- **`project.yml` sits under `gen/`, but it is tracked and hand-maintained** — don't drop it from the list on the assumption that everything under `gen/` is regenerated scratch (some of it, like `gen/schemas`, is untracked). If `tauri ios init`/xcodegen ever rewrites it, re-check the two `CFBundle*` keys against the tree version.
- **`reconcile to 'X' before bumping`**: the script found the files disagreeing. Set them all to the intended current version first (run the script with that explicit `X.Y.Z`, or fix by hand), then bump.
- **`current version X has NOT shipped yet`**: the current version has no release tag and you're stacking a same-tier bump on top of it. Usually the right move is *not* to bump — let your changes ride the pending version. Only override (`ALLOW_UNSHIPPED_BUMP=1`) if you genuinely need a fresh version number anyway.
- The script needs `perl`, `awk`, and `git` (`git` is used only to read release tags for the unshipped-version check; outside a git repo that check is skipped). It runs on bash 3.2 (macOS system bash) as well as the nix dev shell's bash 5.
- It does not touch `DESIGN.md` changelog entries or git tags — handle those separately if your release flow needs them.
